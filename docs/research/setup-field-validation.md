## Question

How should each Setup page field be validated, without breaking autosave of incomplete drafts or making the browser and server disagree?

## Short answer

- Keep [acceptance.check](../../app/acceptance.py#L39) and the schema authoritative for saved values. Decision (2026-10-04): incomplete Setup drafts stay savable, and missing details keep blocking entry to Findings, as they do today.
- Keep the existing shared character rules, closed lists, test-window ordering, component uniqueness, and component-description rules. The Python and JavaScript Setup case table already checks their results on both sides.
- Add the agreed length and row limits (see "Length limits" below). Put server limits in Pydantic or the current save refusal path and mirror them in browser feedback; an HTML `maxlength` alone is insufficient.
- Do not use `type=email` for Username, `type=number` for CI/BSN, or `type=url` for the multiline Web/API scope boxes. None of those controls contains only the corresponding HTML type.
- Decision (2026-10-04, final): Web and API scope lines are free text with no format check, because testers enter too many kinds of scope to list. The earlier URL, hostname, IP, CIDR and host-path rules below are withdrawn.
- Decision (2026-10-04): a save refuses only values that changed. An unchanged stored value that breaks a rule, such as one brought in by an import, still saves but is a Setup issue until fixed.
- Show the field name, environment/account/row and a concrete correction in text. Check syntax as the user types, show required-field errors on blur or Next, and recheck everything on save/server entry.
- Network Access must be chosen explicitly before Findings (decided 2026-10-04). New drafts start blank instead of `Internal`; existing drafts keep their stored value as a valid choice.

## Principles from the sources

- [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html#input-validation-strategies) recommends per-field allowlists, bounded strings and arrays, and both syntactic and semantic checks. A free-text allowlist can be broad; blocking punctuation is not a substitute for output encoding. [OWASP's Unicode guidance](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html#validating-free-form-unicode-text) says to define normalization before validation and comparison when it is needed, not to normalize every field blindly.
- [WHATWG](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#security-2) says client validation is bypassable. Its [constraint API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#the-constraint-validation-api) defines `required`, `maxlength`, `setCustomValidity`, `checkValidity` and `reportValidity`. A nonempty custom error persists until cleared. The [HTML spec](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#attr-fe-maxlength) and [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Constraint_validation#constraint_validation_process) note that length constraints act on user edits, not values assigned by script. They cannot replace a server limit.
- [WHATWG](https://html.spec.whatwg.org/multipage/input.html#url-state-(type=url)) defines `type=url` for one absolute URL; [HTML `pattern`](https://html.spec.whatwg.org/multipage/input.html#the-pattern-attribute) checks the whole nonempty value. Neither handles a textarea with comments, CIDRs and one target per line. [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/:user-invalid) describes `:user-invalid` after interaction; this page's explicit `validation-error` and `setCustomValidity` mechanisms already control its feedback.
- [Pydantic v2](https://pydantic.dev/docs/validation/latest/concepts/fields/#the-annotated-pattern) supports `Annotated[str, Field(max_length=...)]` and item constraints; [StringConstraints](https://pydantic.dev/docs/validation/latest/api/pydantic/types/#pydantic.types.StringConstraints) is preferred to `constr`. Use a [field validator or reusable `AfterValidator`](https://pydantic.dev/docs/validation/latest/concepts/validators/#field-validators) for a format not expressible as a length. Do not enable [strict mode](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/) globally without auditing callers; it changes coercion, and JSON dates have special treatment.
- [Pydantic URL and IP types](https://pydantic.dev/docs/validation/latest/api/pydantic/networks/) parse their own kinds, not a multiline union of URL, hostname and CIDR. `AnyUrl` allows arbitrary schemes; `HttpUrl` is HTTP(S) only, has its own length/normalization behavior and does not establish this app's scope policy. [Python `ipaddress`](https://docs.python.org/3/library/ipaddress.html#convenience-factory-functions) parses addresses and networks; `ip_network(..., strict=True)` refuses set host bits. [Python `urlsplit`](https://docs.python.org/3/library/urllib.parse.html#url-parsing-security) splits but does not validate a URL. Check scheme, authority, host, port and rejected characters separately if using it.
- [RFC 1123 section 2.1](https://www.rfc-editor.org/rfc/rfc1123#section-2.1) permits a hostname to begin with a digit. [RFC 3986 section 3.2.2](https://www.rfc-editor.org/rfc/rfc3986#section-3.2.2) separates IP literals, IPv4 and registered names and brackets IPv6 inside a URI. [RFC 5952 section 4](https://www.rfc-editor.org/rfc/rfc5952#section-4) recommends canonical IPv6 output while accepting valid alternate spellings. Do not rewrite a stored scope target during validation: this app keys target identity by its text.
- [WCAG 2.2 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html) requires identifying the field and describing its error in text. [3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html) calls for a known correction when safe. Native bubbles may be transient and reveal only the first error, so a persistent, associated inline message plus the page summary is preferable to a red border alone.

## Recommendation per field

The timing below separates **check** from **interrupt**. Compute nonempty syntax errors on input so the saved-state indicator stays honest. Show a lasting error on blur or after the first failed Next/Save; update it as the value is corrected. Keep missing mandatory details out of autosave. Before each PUT, use the shared results regardless of the active page, then let `acceptance.check` make the final decision. This addresses the documented off-Setup 422 path in [DATA_MAP section 12](../DATA_MAP.md#L370). Put field-specific text next to its control, with `aria-describedby` and `aria-invalid` when invalid, and retain the summary and first-error focus. Do not rely only on `reportValidity()`'s transient bubble. [WHATWG constraint API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#the-constraint-validation-api), [WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html), [WCAG 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html).

### Test-window dates and Time

Decision (2026-10-04), two parts. First, the start/end order check applies only to ticked environments, on both sides: move it out of `TestWindow.validate_order` (the model cannot see which environments are ticked) into `setup_field_refusals`, which already skips unticked windows, and keep `validateDateOrder` in the browser. The server keeps ignoring unticked windows rather than clearing them itself, so the first part still covers old drafts and imports. For ticked windows, ask for missing Start/End on blur/Next, and say "Production start date cannot be after its end date" once both exist; verify again on save. If hours must follow a time-zone/range grammar, specify it first and add a shared rule; "08:00-17:00" is not implied by the current model.

Keep per-row `TestAccount` strings, the served role character rule and the username shape twin. Username is a login identifier; do not replace it with `EmailStr` or `type=email` because `DOMAIN\\user`, spaces, and `N/A` are currently valid. Decision (2026-10-04): two rows with the same role and the same username are a `setup_results` issue with a `rules.js` twin; they block entry to Findings but still save, with "Account 3 repeats account 1" on blur/Next. Compare after trimming and keep case, since a copy mistake is an exact repeat. Fully blank rows are not compared. The same username under two different roles is allowed. Those are semantic rules for `setup_results` and its `rules.js` twin, not `TestAccount` constructor requirements. Set per-field/list maximum sizes after checking data (**unverified**). Decision (2026-10-04): drop the rule that the first and last characters must be a letter or digit, and keep only "no space at the start or end"; `_svc` and `svc-` become valid. ### Web and API scope lines

Decision (2026-10-04, final): no format check. A Web or API scope line is free text, as today: blank lines and `#` comment lines are skipped and an exact repeat collapses. The format rules recorded in the next two paragraphs were agreed earlier the same day and then withdrawn, because testers enter too many kinds of scope to list. They are kept only as a record.

Withdrawn: accept all four kinds in both Web and API scope: full URLs, bare hostnames, IPv4/IPv6 addresses and IPv4/IPv6 CIDRs. Full URLs may use any valid scheme, not only HTTP(S). Wildcard hostnames such as `*.example.com` are allowed; require a valid hostname after the leading `*.` rather than accepting `*` anywhere. A bare port such as `8443` is not a target; allow a port attached to a host, IP address or URL. The existing multiline control can hold mixed kinds. Keep its `textarea`, `#` comments and blank-line behavior; validate each surviving trimmed line on the server in `reconcile_targets`/`scope_text_refusals`, mirror the rule in `vrRules.scopeRefusals`, and list it in [DATA_MAP section 12](../DATA_MAP.md#L370). For IP and CIDR use `ipaddress.ip_address`/`ip_network` or Pydantic `IPvAnyAddress`/`IPvAnyNetwork` on a temporary per-line value. For URLs, `HttpUrl` is too narrow; use `urlsplit` with an explicit scheme check and scheme-appropriate checks for authority, host, port, credentials and control characters. Do not assume every scheme has a host. For bare names define a DNS/intranet policy, including digit-leading labels. Withdrawn second-round decision: a fifth kind is accepted, a hostname or IP address with an optional port followed by a path and no scheme, such as `app.example.com/api/v1`. Hostnames may be one word (`intranet`), may contain underscores (`my_host.corp`) and may use accented letters as typed (`bücher.de`) as well as the ASCII `xn--` form. A trailing dot (`example.com.`) is refused. Accented letters need the same letter test in Python and in the browser; cover them in the shared rule table. Do not coerce the stored `ScopeTarget.value` into a URL/IP object or canonicalize it during save: target IDs and findings follow the original text. Accepting a URL as scope text does not authorize opening it as a browser link; any link rendering needs its own safe-scheme policy. A browser `URL` check can help with URL-shaped lines, but it is not an exact Python parser twin; put edge cases in the shared rule table. [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986#section-3.2.2), [Python URL parsing warning](https://docs.python.org/3/library/urllib.parse.html#url-parsing-security), [Pydantic networks](https://pydantic.dev/docs/validation/latest/api/pydantic/networks/).

Withdrawn: report "Production Web scope, line 3: enter a URL, hostname, IP address, CIDR or host path" for invalid lines. Check completed noncomment lines on blur or Next, not half-typed URLs on every keystroke. Continue requiring at least one target per selected environment at Next. Decide whether duplicates should warn or remain silently deduplicated; if changed, keep target identity and saved findings stable. Set per-line/count/payload limits on the server with browser feedback after measuring realistic engagements (**unverified**).

### Mobile and Thick Client components and descriptions

Decision (2026-10-04, final): the `component_scope` character rule is dropped, so a component or description may hold any character a tester types. Every scope input (Web and API lines, components, descriptions) keeps its length limit and refuses only characters Word cannot store: U+0000 to U+0008, U+000B, U+000C, U+000E to U+001F, U+FFFE, U+FFFF and unpaired surrogates. Tab stays allowed. python-docx was checked on 2026-10-04: it accepts a tab and refuses U+0007, U+000B and U+FFFE with "All strings must be XML compatible", so one such character would abort generation. The XML 1.0 `Char` production defines the set. The rest of this section predates that decision.

Keep one `component_scope` allowlist for both boxes, per-row pairing by raw index, duplicate-component refusal and required description at the gate. This already handles install paths and Unicode letters without pretending each component is a URL. Add agreed per-row and row-count limits (**unverified**) before adding HTML `maxlength`; do not silently lose excess text. Show "Non-Production Thick Client component 2 is already listed" on duplicate and "Describe Acme.exe" on missing description at blur/Next. Check characters and repeats during typing, but avoid an error while a new row is still empty. Crucially, apply the saved-target checks to `ScopeTarget.value` and `description` when `scope_text` is absent, or make the alternate PUT path explicitly safe; [DATA_MAP section 13](../DATA_MAP.md#L532) records the present bypass. Keep the corresponding browser and server rules paired.
